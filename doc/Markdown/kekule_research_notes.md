This document details the existing components in the FireCore repository and how they will be integrated into the new Kekule Structure Explorer application.

## 1. Component Research

### 1.1 DFTB+ Interfacing (`pyBall/dftb_utils.py`)
- **Key Function**: `run_pbc(apos, enames, lvs, ...)`
  - Drives the `dftb+` execution.
  - Automatically writes input (`makeDFTBjob_pbc`), runs the executable, and parses results (`parse_energy_out`, `read_relaxed_geometry`).
  - **Reuse**: This is the core of the relaxation backend. It handles geometry optimization and PBC correctly.
  - **Integration**: The backend will pass the current structure and PBC flags to this function.

### 1.2 Structure Building & Passivation (`doc/Topics/Kekule_Topology/GrapheneRibbonBuilder.py`)
- **Key Function**: `build_zigzag_ribbon()`
  - Uses a strip-based approach to generate graphene nanoribbons.
  - Includes passivation logic (`_add_chemical_group_atoms`) for NH, CH, OH, etc.
  - **Modification**: The current logic is too "ribbon-specific". We need to extract the passivation logic and generalize it to work on arbitrary honeycomb structures generated by manual drawing.
  - **New Concept**: A `HoneycombGrid` manager that tracks which hexagon tiles have rings and which nodes have atoms.

### 1.3 Visualization Widget (`pyBall/VispyUtils.py`)
- **Class**: `AtomScene`
  - A comprehensive Vispy widget for molecular visualization.
  - Features: Orthographic top-down view, picking/dragging, markers, and line segments.
  - **Reuse**: Excellent base for the 2D/3D viewport.
  - **Modification**: Needs enhancement to support "thick colored lines" for bond lengths. Currently, all bonds share one `Line` visual properties. We should separate heavy-heavy bonds from capping bonds.

### 1.4 UI Integration (`pyBall/ExplorerVisPy.py`)
- **Template**: Shows how to build a complex PyQt5 GUI with a Vispy canvas and a control panel.
- **Features**: Spinboxes for parameters, preset loading, and status bar updates.
*   **Reuse**: Use the layout and event handling pattern from this file.

### 1.5 Bond Order Relaxation (`pyBall/Kekule.py`)
- **Potential Use**: Provides an interface to a C++ Kekule structure solver.
- **Concept**: Could be used to visualize the "theoretical" Kekule bond orders (double/single bonds) before running a full QM relaxation.

## 2. The "Glue" Plan (Architecture)

### 2.1 Backend: `KekuleBackend.py`
This module will be pure Python (logic only) to ensure testability.
- **Grid Management**:
    - Use Axial coordinates `(q, r)` for the triangular lattice of hexagon centers.
    - Track `rings` (set of centers) and `nodes` (dict mapping node positions to atom types).
- **Cartesian Mapping**:
    - Convert grid coordinates to 3D positions using bond length $L=1.42$\AA.
    - Pointy-topped orientation: $x = L\sqrt{3}(q + r/2)$, $y = 1.5L r$.
- **Structure Synthesis**:
    - 1. For each center in `rings`, add its 6 nodes to a temporary node map.
    - 2. Overlay `nodes` from manual atom placement.
    - 3. Generate `apos` and `enames` from the final node map.
    - 4. **Passivation**: Find nodes with occupancy $< 3$ and add Hydrogen atoms in the direction of the missing neighbor.
- **DFTB+ Interface**:
    - Compute `lvecs` based on the system bounding box + user-defined PBC flags.
    - If PBC-X is off, add 20\AA\ vacuum. If on, calculate unit cell width as a multiple of $L\sqrt{3}$.

### 2.2 Frontend: `KekuleExplorer.py`
This module will manage the PyQt5 application and Vispy interaction.
- **View Customization**:
    - Subclass `AtomScene` to add a `draw_grid()` method that shows the underlying hexagonal grid (similar to `MolecularPlacerVisPy._draw_hex_grid`).
- **Interaction Logic**:
    - **Mode 1 (Benzene)**: Mouse click -> Find nearest hexagon center -> Toggle center in `Backend.rings`.
    - **Mode 2 (Atom)**: Mouse click -> Find nearest node -> Cycle through (None, C, N, O).
- **Visual Feedback**:
    - After relaxation, calculate all bond lengths.
    - Group bonds into:
        - *Heavy-Heavy*: Map length to a colormap (e.g., Blue-White-Red). Set as a thick line visual.
        - *Capping*: Fixed color (gray), thin line visual.

## 3. Generalization & New Implementations

- For ribbons periodic in X, the unit cell width must be a multiple of the zigzag period $L\sqrt{3}$.
- **New Implementation**: `KekuleBackend.calculate_lattice()`.

## 6. Detailed Logic Design

### 6.1 AtomQuery Language (Python Implementation)
Inspired by the JS `compileSelectQuerySpec`, we will implement an `AtomQuery` class in `pyBall/AtomicSystem.py` to allow string-based selection.

**Grammar**: `<AtomMatch> [Constraints...]`
- **AtomMatch**: `Element` or `Element|Element` (e.g., `C`, `N|O`).
- **Constraints**:
    - `deg{n}`: Exactly $n$ neighbors.
    - `n{Element}{n}`: Exactly $n$ neighbors of a specific type.
    - `n{Element}{n,m}`: Between $n$ and $m$ neighbors of a specific type.
    - `[H]`: Has at least one Hydrogen neighbor.

**Example**: `N deg{2} [H]` selects pyrrolic Nitrogen. `C n{C}{2} deg{2}` selects bridgehead Carbon atoms on the edge.

### 6.2 VSEPR-Based Passivation Logic
When adding a Hydrogen to an atom $A$ (e.g., Carbon sp2):
1.  **Identify Neighbors**: Get vectors $\vec{v}_i$ from $A$ to its existing neighbors.
2.  **Determine Ideal Geometry**:
    -   1 neighbor: Linear ($180^\circ$ offset).
    -   2 neighbors: Trigonal planar (vector sum inversion).
    -   3 neighbors: Tetrahedral (only for sp3).
3.  **Aromatic Constraint**: For Kekule structures, we assume a 2D plane ($z=0$). The missing Hydrogen for a 2-coordinated sp2 Carbon should be in-plane, exactly bisecting the outer angle.

### 6.3 H-Bond Logic integration
Instead of just finding nearest atoms, we will use the `AtomQuery` to find donor-acceptor pairs:
1.  Query `[H]` on heteroatoms to find potential donors ($D-H$).
2.  Query `N|O` to find potential acceptors ($A$).
3.  Filter pairs by distance ($d(H, A) < 2.5$\AA) and angle ($\angle D-H...A > 150^\circ$).

## 8. Architectural Analysis & Stateful Topology Proposal

### 8.1 Current "Stateless" Architecture (Flaws)
The current implementation uses a **Grid-First / On-the-Fly** approach:
- **Authoritative Source**: A set of `rings` (coordinates) and a dict of `nodes` (elements).
- **Reconstruction**: Every UI action triggers `build_system()`, which iterates over rings/nodes to generate a fresh `AtomicSystem`.
- **The "Epiphenomenon" Problem**: Hydrogens, bonds, and relaxed coordinates are computed dynamically. This means:
    - Manual deletion of a specific Hydrogen is impossible (it is re-generated next frame).
    - Specific chemical states (e.g., Pyrrolic vs Pyridinic Nitrogen) must be inferred every time, which is ambiguous.
    - "Relaxed" positions are stored as `node_offsets`, which only works for atoms pinned to the grid.

### 8.2 Proposed "Stateful" Architecture
We need to transition to an **Atom-First / Persistent-Graph** approach:
1. **Persistent Atom Registry**:
   - Instead of rebuilding, we maintain a persistent list of `Atom` objects.
   - Each `Atom` stores: `element`, `pos`, `node_key` (optional pinning), and `subtype`.
2. **Topology Persistence**:
   - Bonds are stored explicitly as a graph, not re-found by distance every time (except when requested).
   - This allows for stable "Manual Bond Edits".
3. **Grid-Pinning Mechanism**:
   - When a ring is added to the grid, the backend checks which grid-pinned atoms already exist.
   - It only adds *missing* atoms and links them to the new topology.
4. **Hydrogen Ownership**:
   - Hydrogens are persistent atoms with a `parent_index` reference.
   - They "belong" to a heavy atom. If the heavy atom moves (drag/relax), the Hydrogen follows via a relative coordinate or re-VSEPR, but its *existence* is stateful.

### 8.3 Required Data Structures
- `self.atoms`: List of dicts/objects `{ 'element': 'C', 'pos': [x,y,z], 'pin': (q,r), 'parent': None, 'state': 'sp2' }`.
- `self.bonds`: List of `(i, j)` pairs.
- `self.node_to_atom`: Mapping from grid coordinates back to the persistent atom index.
